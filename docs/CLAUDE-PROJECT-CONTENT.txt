## 📋 ADR/RFD Template - Architecture Decision Records

**ADR = Architecture Decision Record**
**RFD = Request for Discussion**

Este é um template estruturado para documentar decisões arquiteturais importantes.

### 🔴 1. PROBLEMA - O que está quebrado?

**O que entra**:
- Sintoma observável: O que você vê que está errado?
- Impacto mensurável: Qual é o tamanho do problema?
- Escopo: Afeta qual parte do sistema?

**Protege contra**: Qual é a afirmação que você quer garantir?

**Exemplo Kube-News**:
```
Sintoma: Pod único não absorve pico de tráfego
Impacto: 30% das requisições recebem timeout
Escopo: App kube-news, não afeta postgres
```

---

### 🟢 2. SOLUÇÃO PROPOSTA - O que vamos fazer?

**O que entra**:
- Abordagem técnica em alto nível
- Mudanças concretas (deltas)
- Mapa de impacto

**Protege contra**: Solução sem desenho = improviso

**Exemplo Kube-News**:
```
Abordagem: Adicionar HPA baseado em CPU
Deltas:
  - Criar k8s-bo/hpa.yml
  - Atualizar deployment com resource requests
  - Configurar monitoring para CPU target (70%)
```

---

### 🟠 3. ALTERNATIVAS - O que foi considerado?

**O que entra**:
- 2-3 alternativas viáveis
- Por que cada uma foi descartada

**Exemplo Kube-News**:
```
1. KEDA (descartado: complexidade desnecessária)
2. Aumentar tamanho do pod (descartado: não resolve)
```

---

### 🟣 4. RISCOS - O que pode dar errado?

**O que entra**:
- Riscos técnicos
- Mitigações
- Sinais de alerta pós-deploy

**Exemplo Kube-News**:
```
Risco: HPA agressivo causa thrashing
Mitigação: stabilizationWindowSeconds=300

Sinal de alerta: Se CPU subir acima de 80%
```

## ✨ Exemplo Real: ADR-002 Kube-News

**Título**: Adicionar HPA para Scaling Automático

**Status**: Proposto
**Data**: 2026-05-17

### PROBLEMA
- Sintoma: Pod único não absorve 500 req/min (máx 200/min)
- Impacto: 25-30% requisições timeout em horário de pico
- Escopo: kube-news application

### SOLUÇÃO
- Implementar HPA com: min 1, max 5 réplicas, target 70% CPU
- Arquivo: k8s-bo/hpa.yml
- Atualizar: resource requests em deployment

### ALTERNATIVAS DESCARTADAS
1. KEDA - overkill
2. Aumentar replicas estáticas - não resolve picos
3. VPA - requer restart

### RISCOS
- Thrashing: mitiga com stabilizationWindowSeconds=300
- Inicialização lenta: mitiga com readinessProbe
- Sinal: latência não melhora com 5 pods = rollback

## 🎯 Quando Usar

✅ USE para:
- Decisões que afetam múltiplos componentes
- Que precisam aprovação antes de implementar
- Que têm impacto financeiro/operacional
- Que serão revisitadas no futuro

❌ NÃO use para:
- Bug fixes simples
- Atualizações de dependência
- Refactorings internos sem impacto
